# Choreography v1.1 Schema Implementation Proposal

## Overview

This document proposes how to implement the three v1.1 schema features that are currently generated but not used by the playback script:
1. `defaultColor` - Template-specific coloring
2. `bounds` - Accurate collision detection using actual ASCII art dimensions
3. `physics` - Realistic physics simulation (mass, friction, elasticity)

## Current State Analysis

### What Currently Works
- **Collision detection**: Simple radius-based (line 681: `collisionDistance = 8 + (obj1.scale + obj2.scale) * 3`)
- **Physics**: Hardcoded velocity multipliers (lines 330-331, 430-432)
- **Colors**: Global ColorSystem with HSL cycling, no per-template colors

### What's Generated But Unused

```javascript
parseColorToAnsi(hexColor) {
  // Parse #RRGGBB to RGB values
  const r = parseInt(hexColor.slice(1, 3), 16);
  const g = parseInt(hexColor.slice(3, 5), 16);
  const b = parseInt(hexColor.slice(5, 7), 16);

  // Convert to ANSI 256-color code
  // Use 16 + (36 × r) + (6 × g) + b where r,g,b are 0-5
  const rIndex = Math.round((r / 255) * 5);
  const gIndex = Math.round((g / 255) * 5);
  const bIndex = Math.round((b / 255) * 5);
  const colorCode = 16 + (36 * rIndex) + (6 * gIndex) + bIndex;

  return `\x1b[38;5;${colorCode}m`;
}
```

## Feature 2: Accurate Bounds-Based Collision Detection

### Goal
Use actual ASCII art dimensions for collision detection instead of magic number `collisionDistance = 8 + scale * 3`.

### Current Collision Detection (TransformManager.detectAndHandleCollisions)
**File**: `play-choreography-v1.1.new.js:669-705`

**Current Logic**:
```javascript
// Line 681: Magic number collision radius
const collisionDistance = 8 + (obj1.scale + obj2.scale) * 3;

if (dx < collisionDistance && dy < collisionDistance) {
  // COLLISION!
}
```

**Problem**: A 3-line ASCII art and a 20-line ASCII art use almost the same collision radius.

### Proposed Changes

#### 2.1 Calculate Actual Bounding Box
**New Method in TransformManager**:
```javascript
getObjectBounds(obj) {
  if (obj.bounds) {
    // Use template-provided bounds, scaled by object scale
    return {
      width: obj.bounds.width * obj.scale,
      height: obj.bounds.height * obj.scale
    };
  } else {
    // Fallback: estimate from ASCII art dimensions
    const artLines = obj.art.art.split('\n');
    const width = Math.max(...artLines.map(line => line.length));
    const height = artLines.length;
    return {
      width: width * obj.scale,
      height: height * obj.scale * 0.5 // Terminal aspect ratio compensation
    };
  }
}
```

#### 2.2 AABB Collision Detection
**Update detectAndHandleCollisions (line 669-705)**:
```javascript
detectAndHandleCollisions(amplitude, velocity) {
  for (let i = 0; i < this.objects.length; i++) {
    for (let j = i + 1; j < this.objects.length; j++) {
      const obj1 = this.objects[i];
      const obj2 = this.objects[j];

      // Skip if either is on cooldown
      if (obj1.collisionCooldown > 0 || obj2.collisionCooldown > 0) continue;

      // Get actual bounding boxes
      const bounds1 = this.getObjectBounds(obj1);
      const bounds2 = this.getObjectBounds(obj2);

      // AABB collision detection
      const dx = Math.abs(obj1.x - obj2.x);
      const dy = Math.abs(obj1.y - obj2.y);
      const minDistX = (bounds1.width + bounds2.width) / 2;
      const minDistY = (bounds1.height + bounds2.height) / 2;

      if (dx < minDistX && dy < minDistY) {
        // COLLISION DETECTED!
        this.applyExtremeTransformation(obj1, obj2, amplitude, velocity);

        // Calculate bounce based on actual collision geometry
        const angleFromObj1ToObj2 = Math.atan2(obj2.y - obj1.y, obj2.x - obj1.x);

        // Collision force based on relative masses (if physics present)
        const mass1 = obj1.physics?.mass || 1;
        const mass2 = obj2.physics?.mass || 1;
        const totalMass = mass1 + mass2;

        // Momentum-based collision response
        const collisionForce = (3 + velocity * 5) * (2 / totalMass);
        const force1 = collisionForce * (mass2 / totalMass); // Lighter object = more force
        const force2 = collisionForce * (mass1 / totalMass);

        obj1.velocityX -= Math.cos(angleFromObj1ToObj2) * force1;
        obj1.velocityY -= Math.sin(angleFromObj1ToObj2) * force1;
        obj2.velocityX += Math.cos(angleFromObj1ToObj2) * force2;
        obj2.velocityY += Math.sin(angleFromObj1ToObj2) * force2;

        // Set cooldown
        obj1.collisionCooldown = 5.0;
        obj2.collisionCooldown = 5.0;
      }
    }
  }
}
```

### Testing Strategy
1. Create choreography with varied template sizes (small 3-line vs large 20-line ASCII art)
2. Verify small objects don't trigger collisions from far away
3. Verify large objects collide when their actual bounds overlap
4. Test mass-based collision: heavy object (mass=3) should push light object (mass=1) more

### Expected Impact
- **Accuracy**: Collisions match visual overlap, not magic numbers
- **Visual Realism**: Large ASCII art has larger collision zone, small art smaller zone
- **Physics Foundation**: Sets groundwork for mass-based collision response

## Feature 3: Physics Simulation (Mass, Friction, Elasticity)

### Goal
Implement realistic physics using template-provided mass, friction, and elasticity values.

### Current Motion System
**File**: `play-choreography-v1.1.new.js:430-432`
```javascript
// Hardcoded motion multipliers
obj.x += obj.velocityX * deltaTime * 5 * motionMultiplier;
obj.y += obj.velocityY * deltaTime * 3 * motionMultiplier;
```

### Proposed Changes

#### 3.1 Apply Friction to Velocity
**Update TransformManager.updateObjects (lines 430-456)**:
```javascript
// Apply physics-based motion
const friction = obj.physics?.friction || 0.8;
const mass = obj.physics?.mass || 1;

// Friction decays velocity (higher friction = more decay)
const frictionDecay = Math.pow(1 - friction, deltaTime);
obj.velocityX *= frictionDecay;
obj.velocityY *= frictionDecay;

// Mass affects acceleration (heavier = slower acceleration from forces)
const massMultiplier = 1 / Math.sqrt(mass); // Heavier objects accelerate slower

// Apply motion with mass consideration
obj.x += obj.velocityX * deltaTime * 5 * motionMultiplier * massMultiplier;
obj.y += obj.velocityY * deltaTime * 3 * motionMultiplier * massMultiplier;
```

#### 3.2 Elasticity in Collision Response
**Update detectAndHandleCollisions collision response (line 692-697)**:
```javascript
// Get elasticity values (0 = inelastic, 1 = perfectly elastic)
const elasticity1 = obj1.physics?.elasticity || 0.3;
const elasticity2 = obj2.physics?.elasticity || 0.3;
const avgElasticity = (elasticity1 + elasticity2) / 2;

// Elastic collision force multiplier
const elasticForce = collisionForce * (1 + avgElasticity);

obj1.velocityX -= Math.cos(angleFromObj1ToObj2) * force1 * elasticForce;
obj1.velocityY -= Math.sin(angleFromObj1ToObj2) * force1 * elasticForce;
obj2.velocityX += Math.cos(angleFromObj1ToObj2) * force2 * elasticForce;
obj2.velocityY += Math.sin(angleFromObj1ToObj2) * force2 * elasticForce;
```

#### 3.3 Boundary Collision with Elasticity
**New Method in TransformManager**:
```javascript
applyBoundaryCollisions(obj, deltaTime) {
  const elasticity = obj.physics?.elasticity || 0.3;

  // Screen edge collision with elasticity
  if (obj.x < 0) {
    obj.x = 0;
    obj.velocityX = Math.abs(obj.velocityX) * elasticity; // Bounce
  }
  if (obj.x > this.screenWidth) {
    obj.x = this.screenWidth;
    obj.velocityX = -Math.abs(obj.velocityX) * elasticity;
  }
  if (obj.y < 0) {
    obj.y = 0;
    obj.velocityY = Math.abs(obj.velocityY) * elasticity;
  }
  if (obj.y > this.screenHeight) {
    obj.y = this.screenHeight;
    obj.velocityY = -Math.abs(obj.velocityY) * elasticity;
  }
}
```

Call this in `updateObjects()` after motion update:
```javascript
// After line 432: motion update
this.applyBoundaryCollisions(obj, deltaTime);
```

### Physics Parameters Interpretation

**Mass** (1-3 from intensity mapping):
- `mass: 1` (small) - Light, quick acceleration, easily pushed by collisions
- `mass: 2` (medium) - Balanced, moderate acceleration
- `mass: 3` (high) - Heavy, slow acceleration, dominates collisions

**Friction** (0.8 default):
- `0.0` - No friction, perpetual motion
- `0.5` - Moderate friction, gradual slowdown
- `0.8` - High friction, quick slowdown (current default)
- `1.0` - Instant stop (not recommended)

**Elasticity** (0.3 default):
- `0.0` - Perfectly inelastic (objects stick together, no bounce)
- `0.3` - Low bounce (current default, realistic)
- `0.7` - High bounce (bouncy)
- `1.0` - Perfectly elastic (energy conserved, unrealistic in terminal)

### Testing Strategy
1. Create 3 templates with different physics:
   - Heavy slow (mass=3, friction=0.9, elasticity=0.1) - should move sluggishly, barely bounce
   - Light bouncy (mass=1, friction=0.3, elasticity=0.8) - should zip around, bounce off walls
   - Balanced (mass=2, friction=0.8, elasticity=0.3) - current behavior
2. Spawn all three in same choreography
3. Observe collision differences: heavy should push light objects, light should bounce more
4. Observe motion differences: low friction objects should coast farther

### Expected Impact
- **Visual Variety**: Different template types move differently (heavy vs light)
- **Thematic Coherence**: Intense/loud sounds = heavy objects, quiet sounds = light floaty objects
- **Emergent Behavior**: Mass-based collisions create unpredictable but realistic interactions

## Performance Considerations

### CPU Impact
- **defaultColor**: Negligible (one hex-to-ANSI conversion per render)
- **Bounds**: Low (simple AABB calculation, replaces existing distance check)
- **Physics**: Low-Medium (additional multiplications per object per frame)

### Memory Impact
- 3 additional fields per object: `color` (string), `bounds` (object), `physics` (object)
- At MAX_OBJECTS=50: ~50 objects × 100 bytes = 5KB additional memory
- **Negligible impact**

### Rendering Impact
No change - same number of terminal writes, just different colors/positions.

## Alternative Approaches Considered

### 1. Don't Implement, Just Remove Fields from Schema
**Pros**: Simplifies schema, reduces token usage in generation
**Cons**: Loses expressive power, makes all templates behave identically

**Decision**: Implement features - the schema promises capabilities that should be delivered.

### 2. Implement Only defaultColor
**Pros**: Easiest, immediate visual impact
**Cons**: Leaves physics/bounds unused, incomplete implementation

**Decision**: Full implementation in phases allows incremental delivery.

### 3. Use WebGL/Canvas Instead of Terminal
**Pros**: True 2D physics, accurate rendering
**Cons**: Breaks terminal-based design philosophy, massive scope increase

**Decision**: Stay in terminal, implement simplified physics that works in character grid.
